## vault-setup

Part of the vault-ops suite. Siblings: vault-doctor (run it against the new vault as the acceptance gate), vault-groom.

Templates live in this skill's `references/` folder, at `${CLAUDE_PLUGIN_ROOT}/skills/vault-setup/references/`. Each markdown template is named `<name>.md.tmpl`; the file it becomes in the vault is plain `.md`. This skill takes the new vault's location from the interview, not from `SECOND_BRAIN_VAULT`. When the scaffold is done, tell the owner to set `SECOND_BRAIN_VAULT` to the new vault's absolute path, because the other skills in this plugin read it.

You are running vault-setup. The product is two things at once, and shipping only the first is the failure mode this skill was rebuilt to close: a vault a fresh AI session can navigate in three reads, AND a vault its owner can open in Obsidian and understand without an AI session translating. It already knows who it is for, and it looks like it.

### Ground rules

- **Copy structure, never content.** Every routing sentence, board row, and template is authored fresh for the NEW vault's world. If you are scaffolding from inside another vault, grep the scaffold for that vault's owner and project names before handing it over: the new vault must carry none of them. This is a privacy boundary, not tidiness.
- **Derive from embedded references, never live.** Every convention this skill scaffolds comes from `references/` inside this skill folder, genericized once at authoring time, never read from any other vault at run time. A skill that reaches back into a specific vault to find out what to build cannot run anywhere that vault isn't.
- **Interview for real content, scoped light.** The structural questions (below) plus one open free-text question. Parse it the way a real onboarding does: extract into `Context/about-{owner-slug}.md`, seed named projects, seed `Tasks/todo.md`, never write a bracketed placeholder, omit a section if there's no data for it. Skipping the free-text question is fine; the skeleton still ships. This is intentionally light: vault-setup is a structural scaffolder with real content, not a full onboarding product, and it has to run in plain Claude Code.
- **Never invent a proper noun.** The interview will describe things it does not name ("a packaging refresh for a hot sauce startup"). Create the folder with a plainly descriptive slug drawn from the words the owner actually used (`Hot-Sauce-Packaging`), and record the missing name as an open question inside the hub. Never fabricate a client, company, or person name to fill the gap, a made-up proper noun reads as fact forever after, and the owner cannot tell which names they gave you and which you guessed.
- **The owner is a reader too.** Every `CLAUDE.md` is written for a session, not a person. `Start-here.md` and `Home.md` are the two surfaces written for the owner: plain language, no routing tables, no rule numbering, no vault jargon. A non-technical owner should be able to open the vault cold and understand it without an AI session translating. Verify this by reading both aloud in your head as that person, not as the agent that built it.
- **A vault is something a person opens.** The scaffold writes a real `.obsidian/` config from `references/obsidian/`, using Obsidian's CORE plugins only. Do not vendor, bundle, or fetch community plugins: they are other authors' work under their own licences, and shipping them inside this skill would redistribute them. Everything the dashboard needs is core: Bases provides the table and filter views that used to require Dataview. **Bases requires Obsidian 1.9 or later.** Check the owner's version before relying on it; on anything older, strip the two `base` blocks out of `Home.md` and leave the wikilink sections, which work on any version. `Home.md` carries a comment block documenting the two syntax traps that bite generated Bases files, read it before editing those blocks.
- **Acceptance gate**: `python3 <new-vault>/Resources/operator/vault-audit.py --vault <new-vault>` must exit 0 (ship the vendored `vault-audit.py` + `test_vault_audit.py` from `references/operator/` into any vault that takes the operator layer). The `hub_yaml` check needs PyYAML (`pip install pyyaml`); without it that check reports "cannot tell", which is information, not a pass. `CANON_BUDGETS` there already ships retuned to a fresh vault's honest starting sizes and `PIPELINES` starts empty, an empty pipeline table is honest for a vault with no capture automation yet. The `obsidian_layer` check is the one that fails on a vault that is only markdown; note that `.obsidian` sits in `ROUTING_EXEMPT_DIRS` and is skipped by every directory walker in that file, so before this check existed no audit could see the gap and a vault with no Obsidian config passed clean.
- **A green gate is not a good vault.** The audit reads files; it cannot tell you the vault opens on an error pane, that the CSS never loaded, or that `Home.md` reads like a config file. Open it in Obsidian before handing it over. This is the same distinction as deployed-versus-working: passing the gate proves the scaffold is correct, not that it is usable.

### Procedure

1. **Interview.** Ask, in one pass:
   - Target directory for the new vault (default: current working directory, if empty or new).
   - Owner name, and what the vault should be CALLED (this fills `# [Vault Name]` in the root `CLAUDE.md` and the `Home.md` heading). Ask for both, the owner's name is not the vault's name, and nothing else in this interview supplies the second one. If they do not give one, default to their FIRST name plus "'s vault", first name only, not the full name they signed up with; it is a heading the owner reads every day, not a database key.
   - **Mode: personal or org.** Org mode additionally scaffolds `Team/` and `Departments/` for an owner whose work is organised around people and functions rather than only around projects. It stays single-user either way; org mode changes the folder set, not the collaboration model. Say so plainly when asking, so nobody expects shared access.
   - Which surfaces will touch it (filesystem only, or filesystem + something else).
   - Whether the operator layer (vendored audit script) is wanted.
   - One free-text question: "Tell me about yourself and what this vault is for, paste a brain dump, a bio, whatever you've got. Anything you mention about current projects gets its own folder." Skippable.
2. Create the folder set (`Context/ Daily/ Tasks/ Projects/ Resources/ Intelligence/ Skills/ _inbox/`) + root `CLAUDE.md` from `references/claude-md-root.md.tmpl`, filled in for the new owner (not copied verbatim, replace every `[bracketed placeholder]` including `[owner-slug]` in the Knowledge routing table row, drop the Active Projects section down to the heading only if the interview named nothing).
3. Per-folder `CLAUDE.md` routing files from `references/claude-md-{context,daily,tasks,projects,resources,intelligence,skills,inbox}.md.tmpl`; `Tasks/todo.md` + `lessons.md` + `journal.md` from `references/tasks-*.md.tmpl`; `Projects/_template.md` + `Projects/Projects.md` from `references/projects-*.md.tmpl`; a starter `Rules-of-Engagement.md` from `references/claude-md-rules-of-engagement.md.tmpl` (needed for the acceptance gate, `vault-audit.py`'s `CANON_BUDGETS` requires this file to exist); `.backups/`.
4. Org mode only: create `Team/` and `Departments/` with `CLAUDE.md` routing from `references/claude-md-team.md.tmpl` and `references/claude-md-departments.md.tmpl`, and write `Resources/going-multi-user.md` from `references/going-multi-user.md.tmpl` so the path to real sharing is on the record rather than improvised later.
5. **The Obsidian layer.** Write `.obsidian/` from `references/obsidian/`: `core-plugins.json`, `app.json`, `appearance.json`, `graph.json`, `daily-notes.json`, `templates.json`, `workspace.json`, and `snippets/vault-home.css`. Create `Resources/templates/` (referenced by `templates.json`) and `Resources/attachments/` (referenced by `app.json`) so neither setting points at a folder that does not exist, and write `Resources/templates/daily.md` from `references/templates-daily.md.tmpl`, `daily-notes.json` names that exact path, and a daily-note button pointing at a missing template is the owner's first broken thing. **Drop a `.gitkeep` into every directory that ships empty** (`Resources/attachments/`, `_inbox/_processed/`, `.backups/`): git cannot track an empty directory, so without it those three exist on the scaffolding machine and vanish on the first clone, taking the attachment folder this step exists to guarantee, and the `.backups/` directory the snapshot rule depends on. Then write the two owner-facing surfaces: `Start-here.md` from `references/start-here.md.tmpl`, and `Home.md` from `references/home.md.tmpl` filled in for this owner. `workspace.json` opens `Home.md` on first launch, so `Home.md` must exist or the owner's first sight of their vault is an error pane, the `obsidian_layer` check fails on exactly that.
6. Parse the free-text interview answer: write `Context/about-{owner-slug}.md` from `references/context-about-owner.md.tmpl`, omitting any section with no data. For each active project, create `Projects/{Name}/{Name}.md` from `references/projects-template.md.tmpl`, add its row to `Projects/Projects.md`, and add a one-line mention to root `CLAUDE.md`'s Active Projects section (the acceptance gate's `hub_triangle` check enforces the board always, and the root list only while the scaffolded vault keeps that section, board-only is a valid layout). For a project the owner described but did not name, follow the never-invent-a-proper-noun rule above. Seed `Daily/{today}.md` with a first entry noting the vault was just set up.
7. **Seed `Tasks/todo.md` from the interview.** A brain dump almost always contains open loops, a brief not yet received, a name not yet known, an exam with a date. Extract them into the `## Active` section as real items. Leave the template's "nothing open yet" line in place ONLY when the interview genuinely produced none; shipping an empty todo next to a hub full of open questions is a contradiction the owner has to resolve manually.
8. `git init`, `.gitattributes` from `references/gitattributes.md.tmpl` (`merge=union` on `Daily/*.md` and `Tasks/lessons.md`), and `.gitignore` from `references/gitignore.md.tmpl`; both are copied verbatim. Write BOTH before the first commit and before step 9, the operator layer's test generates `__pycache__` the first time it runs, and without the ignore file that compiled artifact lands in the new vault's first commit.
9. Operator layer if wanted: copy `references/operator/vault-audit.py` + `test_vault_audit.py` into `<new-vault>/Resources/operator/`, run the test INSIDE the new vault. This plugin ships no autosync job; if the owner wants the vault committed or synced on a schedule, that is a standing change they set up deliberately.
10. Gate: `vault-audit.py --vault <new-vault>` exits 0 (only if the operator layer was taken, without it, confirm the routing/hub/frontmatter shape by eye against the Ground rules above). Run `python3 "${CLAUDE_PLUGIN_ROOT}/skills/vault-setup/references/check_base_syntax.py" <new-vault>/Home.md` (needs PyYAML), the three ways a generated Bases block fails are undocumented and two of them are silent, so the view renders wrong rather than erroring and nobody notices. Then open the vault in Obsidian once and LOOK at it: it must land on `Home.md`, the styling must be applied, and any Bases view must render rows rather than an error. A passing audit says the files are correct, not that the vault opens well. Hand over with a one-paragraph "how a session starts here" note in the new root `CLAUDE.md`, and point the owner at `Start-here.md` rather than at any `CLAUDE.md`.
